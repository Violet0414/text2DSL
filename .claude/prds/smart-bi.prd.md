## 一、背景与目标

### 1.1 一句话定位

基于 WrenAI 语义层底座，为业务人员提供**受控、可信、可解释**的自然语言问数 Web 产品：答案永远带口径出处，未定义的指标绝不给数，只推动治理闭环。

### 1.2 背景摘要

- **定案**（2026-11-16）：底座复用 WrenAI 0.18.0 的 MDL 语义层 + Cube 受控指标查询 + SQL 治理门（`agent_sql.py`）+ 沙箱执行（`governed_query.py`）+ dry-plan 校验，零修改商用；NL→受控 DSL 规划器与 Web 产品层自建。旧版 ChatBI（AGPL-3.0）只作机制思想参考，遵守洁净室纪律，不 fork、不复制代码。
- **PoC 已 GO**（2026-11-16）：58 条黄金问题（50 主集 + 4 组多轮链）最终回归 58/58 全对；工具选择/参数准确率/幻觉拦截/应未命中/澄清触发/多轮继承均 100%；P95 5579ms 超门槛 11.6%（工程优化项，非架构瓶颈）。Cube 回退线未触发。
- **Web 产品层是唯一真正的大块**：开源版无 REST API / Web UI / 账号体系（商业版独占），需自建。

### 1.3 产品目标（v1）

| # | 目标 | 衡量 |
|---|---|---|
| G1 | 答案带口径出处：数字 + 指标定义 + 责任人 + 版本 + 数据新鲜度 | 每个答案卡片展示完整口径元数据 |
| G1 | 可信底线：幻觉拦截率、应未命中正确率 **100%**（红线） | 黄金集回归 + 线上 no_match 审计 |
| G2 | 问数体验：澄清 ≤ 2 轮收敛，多轮追问自然延续 | 澄清触发率 ≥95%，多轮继承正确率 ≥85% |
| G3 | 治理闭环：答不了的进挖掘候选，问数失败率随治理进度单调下降 | 挖掘候选落库率 100%，候选→指标转正流程可用 |
| G4 | 性能：端到端 P95 ≤ 5s | 全链路分段耗时上报 + 压测报告 |

## 二、用户与场景

### 2.1 用户角色

| 角色 | 描述 | v1 核心诉求 |
|---|---|---|
| 业务分析师（主用户） | 看数据、做汇报的业务人员 | 用自然语言问数，答案可信、口径明确、能出图 |
| 语义治理管理员 | 维护指标、术语、枚举、口径 | 问数侧只读治理视图，能触发回归验证变更影响 |

### 2.2 核心场景

**S1 单指标直查**：`上个月各渠道营收是多少` → 直接出数 + 柱状图 + 口径出处。
**S2 口径歧义澄清**：`本月销售额` → 裸"销售额"命中口径歧义对（含税/不含税），先口径后时间分步澄清。
**S3 多轮追问**：`上个月各渠道营收` → `华南区呢` → `那上个月呢` → 槽位确定性继承，改写后重查。
**S4 未定义指标**：`库存周转率是多少` → 明确回复"未找到已定义指标"，列出可查指标清单，需求进挖掘候选。
**S5 非问数意图**：`帮我写个周报` → 旁路回普通对话，不生成查询。
**S6 图表降级**：选图/校验失败 → 表格渲染 + 提示，绝不空白或报错堆栈。

## 五、接口契约（按 WrenAI 0.18.0 实测事实重写）

> Semantra 方案的 MCP 元工具契约（search_metrics/get_metric_detail/query_metric）**不适用**于本路线。本节契约按 PoC 实测底座事实重写；机制（槽位/澄清/降级）不变。

### 5.1 底座实测事实（契约的硬前提）

| # | 实测事实 | 契约影响 |
|---|---|---|
| 1 | `WrenToolkit.from_project()` 在 0.18.0 **不存在**；进程内入口为 `wren_core.cube_query_to_sql` + `wren.cli._build_engine` | 规划器走 wren-core 进程内直调，不走 MCP |
| 2 | cube query `dateRange` 为**左闭右开** `[start, end)` | 时间展开器全部按半开区间生成；契约文档标注区间语义 |
| 3 | `timeDimensions` **必填 granularity**（CLI 隐式补，内嵌调用必须自备） | 归一化层缺省补 `month`；契约必填字段 |
| 4 | `wren -o json` 输出 JSONL（非数组） | 结果解析层适配 JSONL |
| 5 | 连接 profile JSON 必须含 `datasource` 键 | 连接配置 schema 强校验 |
| 6 | 幻觉 measure 翻译层硬拒（`Unknown measure`） | 作为防线②的原生兜底，错误向上透传 |

### 5.2 内部服务契约（产品层 ↔ 规划器）

```
POST /api/ask
  请求: { sessionId, question, context? }
  响应(统一信封): {
    success: true|false,
    data: AnswerCard | Clarification | MissResponse | null,
    error: { code, message } | null,
    meta: { traceId, latencyMs }
  }
```

- `AnswerCard.data`：cube query 结果（JSONL 解析后）+ columns（role/unit）+ metric 元数据 + ChartSpec
- `Clarification`：{ clarifyStep: tax\|time\|dimension, options[], templateId }（模板生成，含分步状态）
- `MissResponse`：{ message, availableMetrics[], candidateId }

### 5.3 会话状态机（继承 §9.3）

```text
IDLE → ROUTING → FILLING → EXECUTING → ANSWERING → IDLE
         │          │缺参        │失败
         │中置信     ▼           ▼
         └→ CLARIFYING(≤2轮) → FILLING   ERROR_ANSWER → IDLE
              │不收敛
              └→ MINING_CANDIDATE（记录后回复）
```

状态与上下文外置存储（Redis/DB），服务无状态化。
